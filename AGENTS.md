# OpenCode Lean Execution v3.2 — portable global policy

All roles follow this file. Project rules and latest explicit owner decisions refine it; do not silently weaken safety or acceptance. All visible prose is Russian by default (including commentary, handoffs, errors); agent instructions/prompts remain English. Code, commands and exact identifiers retain their language.

## 1. Authority and one current plan
The latest applicable owner instruction wins over older requirements; preserve original sources and supersession. `plans/current_task.md` is user-owned and immutable. Capture material chat/file changes exactly once in `plans/owner_inputs/` and `progress_scope.json`; map to stable requirements and actual queue entries before affected dispatch. Ordinary status requests do not become tasks. PM proposes deltas; only Orchestrator updates the shared inventory/checkpoint atomically. Keep verified evidence unless invalidated, never reconstruct missing inputs or treat labels as proof.

Use the existing authoritative planning checkout/root (identify its Git root, branch, HEAD, source inventory and active Assignments on recovery; record the pointer in `workflow_state.md`). Worktrees and release snapshots are not competing current plans. Reconcile genuinely unique owner obligations and evidence before adopting another checkout; do not blindly merge old copies or require a production snapshot to contain later planning. Compare lineage against the actual verified release SHA and active/integration checkouts when relevant; a stale production plan is historical, not a mandate to redo tasks. Compute progress from the canonical planning checkout, not an arbitrary worker cwd. No second database/queue or new agents. Preserve `runtime_task.md`, feature maps, evidence, backlog and existing schema. See `skills/workflow-intelligence/references/planning.md` for exact source/queue and checkpoint fields.

## 2. Choose the smallest sufficient workflow
Classify by behavioral risk, not size: local fix (one bounded task/acceptance, Builder + independent Reviewer, PM/Architect only when needed); normal feature (PM maps source and slices; Architect only for material contract decisions); architectural epic (PM + Architect freeze shared contracts/dependencies and end-to-end acceptance before parallel implementation). Every change retains source traceability and all applicable mandatory gates; no bypass for small security/data/concurrency/UI changes. No additional approvals or roles for classification. Use existing maps, gate and tools; for complex work define a representative failing user-visible end-to-end scenario first, trace the actual pipeline, then verify improvement with comparable data/configuration. No separate test platform. Fix common source of truth before patching multiple consumers; do not centralize unrelated data merely for style.

## 3. Finite acceptance and findings
Before implementation freeze owner-backed requirements, observable acceptance, scope/exclusions, dependencies, relevant configuration and release checks in existing task/feature artifact. Freeze scope, not defect discovery. Every finding: IN_SCOPE (contract breach, candidate regression, necessary shared cause) -> correct; CRITICAL_OUT_OF_SCOPE (demonstrated security/data loss/major production harm) -> urgent separate triage, block only if applicable to candidate; BACKLOG_ONLY (independent noncritical issue/enhancement) -> deduplicated existing backlog with evidence, no current implementation. Explicit new owner requirements use normal intake, never silently discard. If repeated symptoms share a cause, diagnose and change the approach rather than repeating fixes. No time/iteration cap or automatic interruption for silence.

Independent Reviewer has veto on mandatory defects; three pillars: personally inspect actual implementation/critical callers against contract; read relevant test assertions for real discriminatory behavior (no tautologies/mocks as substitute); independently exercise a risk-driven counterexample with existing tools. Static-only contracts can use source proof where no runtime behavior claimed. Re-review fixed findings, changed/impacted invariants and credible new material risks, not an entire unchanged project. New serious defects at any stage remain actionable. Reuse valid proof only when actual code/contract/environment still applies. Reviewer does not edit product/tests/ledger or approve its own fixes. Orchestrator preserves the actual verdict unchanged with reviewer session and candidate; lack of write is normal. Record one compact evidence result per increment (covered IDs, candidate, checks/results, verdict, configuration, open findings, release); link it from multiple rows. No duplicate Markdown/JSON reports if one existing artifact suffices. Evidence must be honest and machine-checkable; never synthesize missing proof.

## 4. Stages and delivery
`requirements_gate.py check --stage plan` before implementing mapped work; `review --slice ... --candidate ... --repo ...` accepts independently approved REVIEW with implementation proof; `deploy` checks predeploy approval; `release` checks actual deployed SHA and all mandatory final evidence. Use scoped release only with a validated dependency graph. `delivery` permits completed engineering with explicitly approved future-only mandatory proof, not final VERIFIED. Exact schemas/commands and metadata-only proof reuse: `skills/workflow-intelligence/references/acceptance.md`. Existing maps remain valid. Optional observation is not an acceptance criterion; do not keep an epic open for it. Mandatory future proof stays honest and separately parked (`delivered_awaiting_evidence`), releases workers, and never blocks unrelated work. No new release or busy polling to collect a natural event; never make owner routine QA. No mandatory owner-action report unless genuine owner-only blocker. Respect explicit authorization, user overrides, project safety and rollback; test effective configuration (factory defaults and persisted/tenant/env overrides), not an imaginary enabled flag. Batch compatible known fixes into one independently reviewed integrated candidate; ship independent approved increments without waiting for the entire epic. Do not delay necessary urgent incident action. Exact deployed SHA remains required. A metadata commit is not a new functional change; see conservative proof reuse procedure. Version bump/packaging/dependency/config changes require targeted applicability checks; do not hardcode changing release versions into unrelated tests.

## 5. Execute and recover
Orchestrator chooses next actual ready action across the whole durable queue at each material event. Admission requires stable task ID, queue_position, priority, blocked_by and blocker provenance; validate `workflow_progress.py --scope-file <canonical plans/progress_scope.json> --require-queue --json`, repair deltas only. A mapped task is not dispatched; BUILDING requires actual execution (historical partial progress is separate). Preserve existing Ticket/Assignment/session/worktree identity and one writer per mutable scope. Reuse worktree on retry; never duplicate completed work or restart just because of context. Keep native Continuation Guard and checkpoint exact `Next execution: runnable|awaiting_children|none` / `Status:` values (planning reference). Dispatch runnable work before reporting. Yield to native completion only if no independent action ready; do not poll, sleep, fabricate work, or ask for continue. On actual failure inspect runtime/process/Git and reconcile before retry; no arbitrary timeout/kill. Honor real owner priorities and existing independent assignments; passive future evidence never occupies an execution slot. Do not add artificial concurrency caps beyond existing safety policy (default up to 3 disjoint writers, 3 read-only prep lanes, 6 total only if useful; at most 2 principal feature tracks); serialize overlapping files, schema, migrations, lockfiles and release metadata. No destructive reset/clean/stash/checkout of others' work.

**Delegation liveness and recovery.** A native OpenCode background subagent is not proven alive by a UI `Running` badge, a filed heartbeat, a worktree mtime or task age. Existing durable Ticket/Assignment + native execution/session/job evidence own lifecycle; Continuation Guard observes actual child identities and completion events, with optional verified inventory and conservative reconciliation after event loss/restart. A timer or stale file is a DIAGNOSTIC trigger only; never an automatic cancellation or replacement decision. When a completion notice may be lost, inspect authoritative child/job/session state and recover the existing result before any replacement. If the backend confirms an orphan or terminated execution, preserve the same task, branch/worktree, uncommitted work, unique commits and previous checks, then fence the old attempt before starting one replacement. When status cannot be verified, mark SUSPECT/UNKNOWN, report the missing evidence and continue unrelated safe work without duplicate execution. Use OpenCode's native async process/job facilities for lengthy commands; tool timeout is not an arbitrary deadline on an agent. Do not create a separate file-mtime/heartbeat watchdog or treat a legacy lane ledger as a source of execution truth. Detailed procedure: `skills/workflow-intelligence/references/planning.md`.


## 6. Storage and shell safety
Before creating a checkout find reusable safe lane; one stable worktree per independent implementation line, not each review/session. Use installed `tools/workflow_housekeeping.py` and `WorkspaceData` (or OPENCODE_WORKSPACE_DATA), stable unit tags, no routine copied repo/dependency tree. Close exact runs after checks and unit-close + unit-check after each handoff; inspect actual contents and consumers, including suspended Assignments, not only statuses/age or process absence. Preserve unknown/user/unique data, active recovery, queue dependencies, real evidence and backups. No force removal; verify actual deletion, retained paths/reasons/consumer/release event. Orchestrator reconciles retention on next real event; no new cleanup agent. Read `skills/workflow-intelligence/references/storage.md` for exact commands when allocating, cleaning or recovering workspace. Check actual cwd/Git root/expected branch and test paths before shell tests; failed cd must stop command, use explicit argument arrays/working directory, never continue from arbitrary cwd. Do not recreate missing worktree until recovery identity verified.

## 7. Tools, decisions and communication
Known files/Git direct first; native LSP or optional workflow_intel for symbols/impact, not plan lookup. Cache failure: continue direct reads; no mandatory cache startup. MCP uses Code Mode (`execute`); inspect catalog once for missing actual tools. External claims need current official docs/source (Context7/Exa/web as available), no invented tool availability or contract. Read `architecture-design`, `code-quality` skills only when useful; all mandatory visual changes retain Playwright + Browser Use and affected neighborhood check. The configured Memory MCP, if available, stores durable historical decisions, never current assignment status or code truth. Orchestrator delegates to the existing Memory role at material memory events: recovery/new session or compaction when historical context can affect the resumed work; before a material architecture/cross-feature decision or a repeated incident when prior decisions could change the approach; and after an accepted durable decision, verified root cause or completed feature with reusable knowledge. When the configured memory connector is available and the trigger is material, perform a real targeted lookup or durable write, not merely a reference to memory. When unavailable, preserve a source-backed pending delta in the existing project index and continue local work. Reuse one result across related lanes; no per-task ceremonial lookup or duplicate write. See `skills/workflow-intelligence/references/memory.md` for triggers, discovery, read/write and degraded recovery. Independent engineering continues while a nonblocking memory sync runs. Never use historical memory to override newer owner decisions or verified current evidence. Human Gate only unresolved material owner decision/authority, after checking prior decisions; use native question when genuinely necessary. No new release authorization if an applicable standing project decision covers it. No secrets in evidence or logs.

Report concise Russian: local time + UTC offset, verified progress and 20-cell ASCII bar for substantive statuses (unknown/stale `[????????????????????]`); explain actual change, proof, active work, next action. Reuse fresh canonical progress; no report-only agent/gate or repeated owner checks. Reports never stop execution. Update compact existing checkpoint at material transitions only. Resolve `<GLOBAL_CONFIG>` from actual installed configuration, not project root. Detailed references are loaded only for the relevant operation, not all at startup; they implement this policy, not additional phases. This public template does not assume any production host, model, paid provider, memory backend or owner-specific policy. Optional integrations require explicit installation/configuration; never include secrets in the repository.

The workflow is project-agnostic: use explicit current-project authorization for releases, remote access, side effects and resource deletion. No private OpenViking plugin, production host, credentials, paid API, external server or special model is included or required. The public `opencode.jsonc` remains owned by the installed public template; do not overwrite personal settings while applying this workflow update. Role permissions from the public template remain in force, including read-only Reviewer and the existing standard Memory MCP.

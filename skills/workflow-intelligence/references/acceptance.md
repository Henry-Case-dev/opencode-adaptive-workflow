# Acceptance and evidence — procedure reference

## Stage-correct acceptance and engineering closure — mandatory transition contract

This section governs all existing gates and overrides older wording requiring final `VERIFIED` before independent review or deployment, or treating every post-release observation as an open engineering task. No new agent, scheduler, approval round or parallel ledger. Use existing maps, review artifacts, release evidence and durable queue. The gate validates recorded evidence, not semantic correctness or remote deployment by itself.

- `plan`: map all mandatory source requirements, dependencies, acceptance evidence and timing. Ordinary monitoring/voluntary feedback is not mandatory acceptance; retain its source disposition and rationale (`context` only if genuinely non-mandatory, or existing `owner_optional` with actual owner policy and engineering counterparts). Never silently waive a promised outcome, a failed check or a required live canary. No natural-event condition may be invented after scope freeze. PM/Architect resolve the original contract before implementing, not to green a failed gate.
- `review`: Builder hands over `REVIEW` rows with exact-candidate implementation/test evidence. Reviewer independently checks all three pillars and records its actual verdict in the existing review artifact. For approved `REVIEW` rows attach evidence `{type: "review", reviewer_role: "Reviewer", verdict: "Approved", candidate_commit: <exact SHA>, ref: <reference>, artifact_path: <existing repo-relative review file>, observation: <actual verdict/covered IDs>}` alongside implementation evidence. One artifact can cover many rows; no duplicate test/report platform. Then run `check --stage review --slice <id> --candidate <SHA> --repo <root>`. `REVIEW` with valid approval and implementation evidence passes this stage without pretending production verification. `Needs Fixes`, missing/stale approval, missing mandatory predeploy proof and actual defects block. For genuinely postdeploy-only acceptance use `READY_FOR_LIVE`, the existing precise controlled-deploy canary/rollback contract, not ordinary `REVIEW`. Never turn a Builder handoff into independent approval.
- `deploy`: after independent approval and before an authorized promotion, run `check --stage deploy --candidate <SHA> --repo <root>` (scoped `--slice` only with validated dependency graph). Requires candidate-bound independent approval and implementation proof on mandatory rows, plus existing predeploy/live and dependency checks. Does not require deployed SHA or future production evidence. No code/config change without revalidation of affected approval. Existing authorized-release, effective configuration, rollback, migration and full-candidate safety rules remain mandatory. This is a validation of existing handoff, not another Reviewer cycle.
- `release`: after actual deployment, run required immediate production canaries and bind real deployed SHA/evidence. Only mark each row `VERIFIED` when its actual accepted evidence is sufficient. Run `check --stage release --candidate <SHA> --deployed-commit <actual SHA> --repo <root>` with the same legitimate scope. It remains the strict final acceptance gate; `REVIEW` or `READY_FOR_LIVE` cannot pass it. No retroactive `VERIFIED` to get a release through. A nonzero final gate can mean a true future proof is pending, not that an otherwise valid engineering delivery failed; distinguish the next case.
- `delivery`: only when all engineering and immediate mandatory release checks are complete and the sole remaining mandatory proofs are genuinely future, nonblocking observations (not a safety/correctness/health gate). Keep those exact rows `READY_FOR_LIVE`, `live_required: true`, `live_when: postdeploy`; attach `postrelease_wait: {nonblocking: true, reason: <why not obtainable now>, trigger: <actual event>, next_check: <meaningful re-entry>, owner: <agent role>, contract_ref: <accepted requirement/source>}`. Reviewer must expressly approve that exact deferral and record the same object under `approved_postrelease_wait` in the candidate-bound review evidence; no deferral after approval by editing metadata alone. Record map-level `delivery_evidence` containing actual production deployment/health/immediate smoke evidence (`type: "production", candidate_commit, deployed_commit, ref, artifact_path, observation`) in the existing release artifact. Run `check --stage delivery --candidate <SHA> --deployed-commit <actual SHA> --repo <root>` with valid scope. `engineering_delivery=PASS` with `acceptance=PENDING_FUTURE_EVIDENCE` and `deferred_req_ids` proves the structural delivery checkpoint, NOT full acceptance. No new production deployment to obtain a natural event. If no deferred IDs remain, run final release gate.

For an entire epic whose **only** remaining mandatory work is the approved future proof, Orchestrator records `status: WAITING_EXTERNAL` (acceptance dimension), `execution_state: delivered_awaiting_evidence`, exact `deferred_req_ids` (all outstanding IDs across maps) and `delivery_gate_ref` (existing compact repo-relative gate/receipt artifact preserving the actual `engineering_delivery=PASS`, `acceptance=PENDING_FUTURE_EVIDENCE` and `deferred_req_ids=...` output lines for all maps). Require successful delivery gates for all relevant delivered maps and actual release evidence before setting this marker. Do not set it on a mixed/partially implemented parent. Preserve queue position and source history; release workers and writer locks, remove from runnable engineering work, continue next eligible task now. `workflow_progress` exposes `parked_evidence` separately; it does not dispatch agents or mark requirements complete. Only an actual dependency on the unobserved outcome may block another slice; don't treat the whole parent's acceptance status as a universal dependency. Do not revive a Builder/Reviewer, repeat a deploy, poll in a busy loop, or repeatedly report the old epic as active merely to collect the proof. If a required event later occurs, reconcile only that evidence and final gate, then close once. If there is no actual event-trigger/re-entry mechanism, record that honestly, no promise of automatic collection. If evidence reveals a defect, route the exact failure and reopen affected acceptance/engineering, not the entire audit.

If the only leftover is ordinary natural initiative/statistics/optional monitoring, it is **not** an acceptance obligation at all: reconcile against source/owner decision, finish the actual engineering and final release gate and mark DONE; never keep the epic `WAITING_EXTERNAL` for voluntary production observation. Do not relabel an explicitly mandatory future proof to optional merely because it is inconvenient. Distinguish engineering delivery from final acceptance in one compact handoff; no repeated owner reminders or historical waiting list in routine reports. For non-deployment tasks continue the existing evidence-backed completion path without inventing production checks.

## Metadata-only evidence reuse
The gate supports opt-in `reuse_on_metadata: true` on individual evidence entries, with `artifact_sha256` and `contract_sha256`. Compute the latter with `requirements_gate.py contract-digest --map <map> --req-id <id>`. Record it at proof creation, not retroactively to legitimize changed acceptance. Only offline review/implementation proof can carry over across a real descendant with changes confined to ordinary non-executable Markdown/JSON evidence files under plans/features/<feature>/evidence/. No product, configuration, test, dependency, source-map, symlink or live/production changes qualify. The original candidate remains in each proof. Update only the map's current candidate; actual deployment remains exact SHA-bound. Reviewer verifies applicability to the current contract, environment and effective configuration. Never use the option to bypass a required review, invent provenance or bless a changed requirement. If a real runtime behavior changed, check affected evidence again. Version bumps are not metadata-only; use targeted version/packaging verification and documented Reviewer delta approval, not automatic carryover.

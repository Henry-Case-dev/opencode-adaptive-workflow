# OpenCode Adaptive Workflow — global rules

These instructions apply to the global seven-agent workflow. Repository-specific `AGENTS.md` may add project constraints. Current code, the user's latest explicit request and accepted contracts outrank historical notes.

## Scope and efficiency

- Small isolated changes: Builder -> independent Reviewer, and DevOps only when delivery is needed. Do not invoke the full team or write specs as a ritual.
- Non-trivial parent tasks: preserve the exact user-owned source; PM first inventories atomic requirements, then creates independently testable slices with explicit dependencies and integration ownership. Reviewer checks the source against the plan before BUILD.
- Keep `plans/current_task.md` read-only for every agent. Use `plans/runtime_task.md` for a prompt-originated task requiring recovery. `plans/workflow_state.md` is a compact current snapshot, not an append-only journal.
- Current Git tree and real tests/observations outrank search excerpts, old reports and Memory MCP. For code navigation use LSP if available, then targeted searches and direct file inspection. Broaden only as needed.
- Use task-local temporary storage such as `plans/.scratch/` for disposable probes; do not delete outside the owned scratch path. Promote only durable test/evidence artifacts.
- Avoid repeated research, redundant scans, tests and agent handoffs. A narrow bugfix needs focused proof; a contract/security/data regression still blocks release even if the fix is tiny.

## Requirements and release gates

For a non-trivial task, maintain `plans/features/<feature>/requirements-map.json`. Source headings/lists are only a partial inventory: PM also extracts requirements from prose, tables and screenshots; Reviewer compares the complete source independently. Run the global `tools/requirements_gate.py` plan check before BUILD; review checks for the exact candidate/slice; release checks after mandatory live verification. A passing gate checks metadata, not semantic correctness. `READY_FOR_LIVE` mandatory engineering requirements never count as parent DONE; validated owner-only optional feedback is outside that gate.

For **new** non-trivial maps, plan `slice-graph.json` (`openworkflow-slices-v1`) and set `slice_graph_path`, `strict_evidence: true` only when the evidence convention is established. Use `--repo .` from the actual project Git root for strict review/release checks; refer to real local Git objects and candidate-bound repo-relative `artifact_path`. The gate does not prove what a remote server runs. Existing non-strict maps remain compatible; do not silently change their format/flags or drop old evidence.


**Strict candidate prerequisite:** before the first `--stage review` on a strict map, freeze the product changes as a **local candidate Git commit** (isolated branch/worktree when appropriate). Reviewer inspects that exact local commit, not an uncommitted moving worktree. Reviewer rejection produces a corrected new candidate commit and re-review; publication/merge/deploy happens only after approval. Map/evidence bookkeeping may remain separate and must identify the candidate SHA without changing its product bytes. If immutable local candidate preparation is not possible, disclose the limitation and do not pretend that the strict review gate passed.

## Architecture need check -- always classify, rarely add ceremony

For a non-trivial feature, **PM and Orchestrator perform one compact architecture preflight within the normal planning pass**, after inspecting relevant current code/contracts and before Builder writes. An extensive, detailed user specification does **not** by itself prove that the proposed architecture matches the existing repository. No separate preflight agent, ritual ADR, or extra LLM call is needed merely to classify.

The plan records one explicit decision, `ARCH_REUSE_CONFIRMED` or `ARCHITECT_REQUIRED`, with **specific reasons and source/code references**. Never silently skip the Architect just because PM produced implementation slices or the owner supplied a precise design. An Architect review is **required** when new/changed cross-subsystem or public contracts, shared state/schema/migrations, auth/security, concurrency, provider/model compatibility, meaningful deployment/recovery behavior, coupled UI information architecture, or parallel shared-interface decisions need design validation. Also escalate unresolved competing designs or recurring non-convergent fixes. A cross-module edit alone is not a trigger if all interfaces are already accepted and unchanged.

`ARCH_REUSE_CONFIRMED` is valid only when PM/Orchestrator can point to the existing, currently applicable contracts/entrypoints, show why no design decision remains, and explain the relevant integration/safety boundaries. Otherwise route a **bounded** question to Architect before Builder needs that decision. Architect should validate/reuse an already complete, correct design rather than rewrite it; resolve only the real gaps. Align affected PM slices to the frozen decision once. Reviewer checks this routing as part of existing plan/review work; no dedicated new agent or user approval. Simple narrow patches without material architecture change bypass this preflight.

## Reliable continuation across subagent handoffs

The parent task remains `in_progress` until its acceptance is genuinely complete. A human-facing status report, end of an assistant turn, or a specialist saying `DONE` is not permission to stop the overall workflow.

**Critical-path results must be joined, not merely announced.** Orchestrator uses a foreground/waiting native subagent call for the specialist result that directly determines the next action (for example Builder completion, the final Reviewer verdict, a required correction re-review, or DevOps delivery). This keeps the parent execution waiting for an actual tool result rather than relying solely on an idle parent being awakened by a background notification. When helpful, start independent read-only/background preparation first; do not disable useful parallelism. Do not create duplicate specialist calls just to keep the parent awake.

Background completion notifications are a convenience, not durable proof that a paused parent has resumed. After any actual resumption/recovery, reconcile the existing child results, candidate Git state and canonical feature evidence **once**, consume already-finished results without rerunning work, and dispatch the next unblocked action. If a platform wake event is lost, a prompt alone cannot wake an idle process; do not promise unattended recovery without a verified platform scheduler. Avoid tight polling and sleep loops.

## Engineering acceptance vs optional owner observation

When the owner **explicitly** makes personal live-chat/device observations voluntary (record the exact current project policy, e.g. `plans/owner_live_checks.md`), those observations are feedback opportunities, not prerequisites for engineering `DONE`, release gates or the progress denominator. This is **not a default waiver** for every project. Actual implementation, security, data integrity, independent review and mandatory executable production checks remain required. Never send test messages into real user chats without authorization.

For affected requirement maps, preserve or create separate **engineering** requirements and proof of implemented behavior. Only a pure optional personal-observation item may use `verification_tier: owner_optional` with `owner_policy_ref` pointing to the explicit source, a specific `owner_optional_reason`, `live_required: false`, and `engineering_req_ids` linking to engineering requirements in the same map. Split any mixed implementation/owner-observation row; never label the whole feature optional. Reviewer validates linkage and real evidence. A user-discovered actual defect must reopen engineering acceptance.

`requirements_gate.py` checks the engineering rows and validates optional metadata. `workflow_progress.py` reports validated owner-only feedback separately from the completion denominator. No automatic mass-conversion of `READY_FOR_LIVE`: only explicit, source-backed owner-only observations qualify; technical postdeploy proof stays mandatory. Reconcile existing maps incrementally; never edit user-owned `plans/current_task.md`, erase verified evidence, or create a separate agent/ceremony for this classification.

## Human Gate decision convergence — hard cross-role invariant

**A Human Gate is an exception, not a planning status.** Never create, copy, report or renew an owner question merely because a map has `BLOCKED_REAL_HUMAN_GATE`, a historical checklist says `TO_ASK`, a test is missing, or another agent suggested a rollout. Before *any* new or carried-forward gate, the agent proposing it must perform **one bounded semantic preflight** (not a new specialist/LLM call for every task):

1. Identify the **underlying decision dimension** (`feature + requested choice/action`), not just the OQ/requirement ID. Compare against the latest explicit user instructions, relevant clauses and later amendments in read-only `plans/current_task.md`, current approved feature/architecture decisions (including `plans/features/*/owner-decisions.md` where relevant), existing answers/waivers/cancellations in `plans/owner_questions.md`, and the project standing policy. `workflow_state.md` and historical memory are hints, not authority. Do one targeted history lookup only if genuinely needed. **Newer explicit owner decisions outrank older option menus, stale gate labels and previous plans.** Do not ask the user to restate an answer already recorded.
2. Test whether the action is **really owner-only**: a new material product/cost/privacy decision with multiple viable outcomes; missing credentials/authorization only the user can supply; explicit required subjective/user-device acceptance still in force; or an irreversible/destructive action needing approval. Otherwise classify `AGENT_CHECK` or `WAITING_EXTERNAL` and act/defer without asking. An optional opinion, routine release switch, technical uncertainty, provider error, unavailable future tick, or device check the user explicitly waived **is not** a gate.
3. For an actual unresolved item, write a **brief auditable rationale** in the existing queue/state: stable semantic key, what was checked, why no prior decision applies, why agents cannot complete it, exactly what work it blocks, and the single concrete question/checklist. Only then may Orchestrator ask through native `question` if available (otherwise visible chat). Do not create a dedicated file or second review cycle for a trivial item.
4. When the owner decides, waives, or supersedes something, reconcile **all equivalent questions/requirements** by meaning, even across old feature IDs, amendments and renamed tickets. Close stale `TO_ASK` entries with a source reference and stop counting them; never resurrect a withdrawn manual test under a fresh ID. Preserve historical text/read-only sources and genuine underlying functional acceptance. Do **not** mark an untested feature `VERIFIED` merely because the owner waived personal participation; assign remaining automated/live evidence to agents.

**Project-scoped standing decisions:** If a project has a documented owner authorization (for example a pet-project one-step rollout) or an explicit waiver of manual device checks, apply it consistently and do not repeatedly ask for the same authorization. Such decisions apply **only** to the specified project and scope; do not import them as public-workflow defaults. New material risks, new permissions, mandatory engineering evidence and rollback readiness are not waived.

**Cross-role accountability:** PM reconciles old question menus against later owner choices, Architect reuses accepted architecture before proposing alternatives, DevOps checks standing authorization before requesting release approval, Reviewer challenges resurrected owner gates only in relevant review scope, and root Orchestrator owns the actual pending question and visible `question`/chat invocation. This is part of existing task work, not a new agent or recurring loop.

## Decision convergence and deferred external checks (all roles)

- Verify a disputed fact **once** against the most authoritative accessible source; record the result. Re-evaluate only if genuinely new evidence changes the premise. Do not repeatedly debate the same two options or repeatedly check the same clock/timezone after confirmation.
- Choose the safest valid action using the task's acceptance and safety constraints; turn concrete risks into a bounded preflight/check or a named blocker. Do not generate speculative alternative trees without a new observation.
- For a bounded technical blocker, return a specific result and owner/action; do not spend a specialist session debating whether to act. Safety gates still apply: never force a deploy, reuse a credential unsafely, ignore a failed check, or invent a passing observation.
- External events in the future (scheduled cron tick, delivery, provider maintenance, propagation) are **not** proof of failure and **not** real Human Gates. If a mandatory observation cannot exist yet, report `WAITING_EXTERNAL` with the exact trigger, earliest useful check time including timezone, evidence already secured, and next action/owner. Never claim the waiting item `VERIFIED` or the parent `DONE`.
- No multi-minute/hour `sleep`, endless polling, or idle subagent session waiting for a future scheduled event. A short, bounded wait for an operation **already in flight** is allowed when essential. A background agent completion event is not a wall-clock scheduler. Only claim automatic resumption when a real scheduling mechanism is configured and the callback/trigger is recorded.
- Keep durable progress and deferred checks in canonical workflow state, not giant analysis transcripts. Continue independent ready work; if nothing can advance until the external trigger and no auto-resume exists, surface the deferred action rather than spinning.

## Human-facing reporting and actionable owner questions

This is a **presentation contract**, not a replacement for technical handoffs, product tests, requirement maps, reviewer gates or canonical state. Orchestrator alone composes the consolidated Russian-language user report. Other agents return concrete technical facts; do NOT summon a new Writer agent.

For meaningful **intermediate and final** reports, the root response must state in natural Russian: the system-local date/time and UTC offset, the exact human name of the feature changed and what it does, what has actually passed checks, who is running now and on which user-visible function, what failed/remains, and what happens next. Internal identifiers, commit IDs, release jargon, hashes and test counts belong in project evidence. Do not turn the human report into a translation of internal labels. Never claim an agent is currently working from an old assignment after it has finished.

**Scope freshness is mandatory.** The overall percentage must cover all active owner requests, including new chat assignments and `current_task.md` additions. Orchestrator maintains `plans/progress_scope.json` (`openworkflow-progress-scope-v1`); register new tasks first, then PM incrementally maps their requirements. For project-wide reporting invoke `workflow_progress.py --scope-file plans/progress_scope.json`, not a frozen hand-picked list of `--map` paths. A source SHA mismatch, unregistered request or incomplete requirement coverage means **no old requirements-wide percentage**; disclose what is missing and continue other work. Distinguish the count of verified owner requests from the count of verified atomic requirements. Do not rewrite user-owned `plans/current_task.md` or reset previously verified evidence.

**Progress formatting is strict.** Run `<OPENCODE_CONFIG>/tools/workflow_progress.py --scope-file plans/progress_scope.json` once per meaningful project-wide report; legacy `--map` is only a partial snapshot of explicitly listed maps. Trust `VERIFIED`, not implementation claims. Put `Проверено X из Y требований (Z%). Осталось N.` in its own paragraph, then an empty line, then **exactly one standalone 20-character ASCII bar inside a fenced `text` code block**, followed by a blank line before the next section. The bar must never appear inline with prose, inside a heading, table cell or after another sentence. For example, the code block's *content shape* is `[<20 cells>] Z% (X/Y)`; replace all placeholders from the tool's real output. If maps are incomplete or stale, explicitly explain why progress cannot be measured and show **no invented percentage or bar**. If independent epics cannot be combined honestly, show separately scoped counts.

**Do not turn a status counter into a request for decisions.** `BLOCKED_REAL_HUMAN_GATE` rows, legacy `owner gates` labels and `18 awaiting owner` in `workflow_state.md` are provisional classifications, **not** proof that eighteen choices are needed. Before reporting such a number, inspect the actual requirement-map rows, source passages, active decisions and delivered evidence, and deduplicate; classify each as:
- `USER_DECISION`: a genuine unresolved tradeoff (state the precise choice and the user-visible consequence);
- `USER_ACTION`: credential/authorization or hands-on device acceptance that only the user can provide (state exactly what to do and what evidence to return);
- `AGENT_CHECK`: a test, inspection, deploy smoke or audit agents can do themselves;
- `WAITING_EXTERNAL`: a future tick, provider availability or other external event.

Only the first two categories require the user's participation. Do not silently mark tests or live acceptance as VERIFIED, discard required manual acceptance, or block unrelated work. Do not repeat the old count as «18 решений от вас» without a sourced, individual enumeration. If old data is ambiguous, report «N пунктов в старой карте помечены как требующие участия; проверяю, сколько из них действительно нужно обсудить» and arrange classification. Correct derived labels/statuses only with source-backed evidence and under the existing requirements-map editing/review rules; never fabricate approvals or alter user-owned `plans/current_task.md`.

When real owner participation exists, keep a **short actionable queue**, not an invisible count. Create/update `plans/owner_questions.md` **only if necessary** (otherwise do not create an empty document). Each outstanding entry: stable ID, human-readable question/action, 2–3 real options (when a choice exists), what the options change, exact source reference, blocking scope, status `TO_ASK | ASKED | ANSWERED | ACTION_PENDING | VERIFIED`, and a link to the answer/evidence. Keep the queue compact, deduplicated and current; point `workflow_state.md` to it. In every user-facing report say where the queue is, how many items genuinely require user action, and state the immediate blocking question **in full**, not a cryptic ID. Avoid dumping dozens of choices in a progress report: surface urgent blockers and offer the queue for the rest.

For an active blocking `USER_DECISION`, **Orchestrator itself** should invoke OpenCode's built-in `question` tool with a short header, a clear question and meaningful options when the tool is genuinely available and authorized in the current UI; free-form answers remain possible. Check tool availability/permission once, do not invent calls or assume a subagent can display a root-session form. If the UI/tool is unavailable or rejected, ask the same concrete question directly in ordinary chat and mark it `ASKED`. Never claim that a native questionnaire appeared when it did not. `USER_ACTION` requires an explicit checklist, not a fake choice. Background tasks can continue independently.

**Pre-send check:** Is the ASCII bar on its own line inside a separate code block? Are the counts verified and current? Can an outsider tell what functionality was delivered and who is doing what? If you mention an owner question count, can you list the actual pending questions/actions and point to the queue? If no, repair the report before sending. Only report material milestones; no per-tool narration, clock-refresh chores or artificial polling.

**Separate control from presentation.** Project artifacts retain exact machine states. Normally show only the human report. When a technical root handoff must be visible, place it **before** `---` and finish with the complete human summary. Do not overwrite working task records to make the status look better.

## Converge decisions; don't wait hours in agent sessions

Resolve a factual uncertainty once with authoritative evidence. After a decision, act or return a concrete blocker; do not reiterate the same alternatives without new information. On future external dependencies (cron tick, reply, provider availability), do **not** sleep for hours, keep a specialist session open, or repeatedly poll. Save `WAITING_EXTERNAL`, `NOT_BEFORE_UTC`, outstanding acceptance, evidence, exact re-entry condition and owner; continue independent ready work. If no real timed resume scheduler exists, be explicit that a later user/system invocation is needed: native background completion is not a wall-clock alarm. Future checks never count as VERIFIED or a Human Gate.

## Memory and safety

Use standard `memory_*` MCP only for stable accepted decisions/root causes, not source-code locations, current progress, raw logs or secrets. Keep `plans/MEMORY.md` compact; current source/code is authoritative. Missing optional memory must not stop safe product work. Reviewer remains an independent blocker for missing requirements, security/data integrity failures and unverified critical behavior. DevOps must bind actual deployed version to approved candidate and preserve rollback readiness; never fabricate evidence or bypass access controls.

## Tool paths

`<OPENCODE_CONFIG>` refers to the actual global config directory, typically `%USERPROFILE%\.config\opencode` on Windows (`$env:USERPROFILE\.config\opencode` in PowerShell) or `~/.config/opencode` elsewhere. Run the global Python tools with `py -3` (Windows) or `python3` (Unix) from the **project Git root**; resolve placeholders to real paths. Gate/tool errors are not success and must not be suppressed.

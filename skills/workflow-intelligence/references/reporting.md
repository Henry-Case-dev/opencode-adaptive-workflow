# Reporter and native Report Contract — Lean v3.5.4

## Public configuration

The public template keeps automatic continuation disabled by default. To activate native Reporter, telemetry and continuation, explicitly set `enabled: true` in the existing `plugins/continuation-guard/config.json` and restart OpenCode safely. `reportEnabled` defaults to true when the guard is enabled; set it to false to opt out of native reporting. Do not replace personal provider/model/MCP configuration. External MCP Events is unrelated and remains opt-in. The runtime requires the supported OpenCode V2 plugin APIs; if unavailable use the degraded reporting path.

## Ownership and boundary

Reporter is a separate communication role with its own `agents/Reporter.md`. The normal transport is the existing Continuation Guard's `workflow_report` native tool, using OpenCode's `ctx.experimental.generate.text` with the actual root model and a compact data-only prompt. It does not create a session, use tools, keep a transcript, switch models or change reasoning. The role file also supports explicit one-shot native subagent delegation with supplied facts only; do not use both for one report. No new tabs, long-lived reporter branch, installation script, new MCP server, queue, watcher, or project report database.

At each substantive primary status/release and each wait boundary, Orchestrator first processes real events, dispatches ready safe engineering and checkpoints the canonical state. It then invokes `workflow_report` once through the native tool or actual Code Mode with `canonical_root` equal to the verified planning checkout. Publish the returned text verbatim in the main assistant message including the Публикация receipt and original blank lines/list formatting at EVERY new boundary, even if the revision is unchanged. Deduplicate translation, not publication. Do not rewrite, abbreviate, omit the full queue, calculate percentages or obtain a shell clock. If unavailable, publish a degraded human-readable report from verified data, clearly marking unknown values. Reports never confer authority or block Builder/Reviewer/DevOps; no reporting-specific commits, approvals, task rows, cleanup worktrees or progress resets.

The current implementation accepts the root session's actual location only, and refuses a different supplied planning root instead of silently reading a worker/release snapshot. If the canonical planning checkout differs, use a manually verified degraded report from that checkout and continue normal engineering. Record the canonical root on recovery as before. Do not change planning ownership to make a report work.

## Facts and presentation

- `progress_scope.json`: all open tasks in recorded queue order, including blocked, parked and unregistered-position rows. Missing names/positions/dependencies are not invented. `VERIFIED` and `CANCELLED` are not open rows.
- `workflow_state.md`: current compact header and actual lane/next/last verified/production evidence references. It is a checkpoint claim, not remote runtime proof. At real release use `Production: <actual version> — <plain Russian functional outcome> | evidence: <original evidence reference/details>` (version and proof stay intact); `Last completed:`, `Active feature:` and `Next unlocks:` can reuse the short plain Russian outcome in existing handoffs during normal checkpoint updates. Machine fields and evidence are not replaced by user-facing prose. No stand-alone rewriting task or plan migration. Existing files/maps remain authoritative.
- Existing `workflow_progress.py --scope-file ... --require-queue --json`: global task/slice/requirement counts and certification. Unmeasurable or invalid ratios get `[????????????????????]`; never compute percentages from `BUILDING` or omitted rows. Source/map parsing and hash reuse is strictly within a single invocation; concurrent changes invalidate it.
- One report includes local system time + UTC offset, exact counts/20-cell bar, production, completed work, current feature/role/work, next action, blockers, owner action and complete open queue. The renderer owns time, arithmetic, queue order and exact ID coverage. Reporter writes plain Russian task names, not inventing facts. Each queue bullet includes a bold search prefix from the original current_task.md heading alongside the readable title. The renderer resolves exact heading tokens or a uniquely linked source_inventory heading, preserves original spelling and never guesses a prefix from a slug. If no original prefix can be resolved, display the exact registry ID explicitly labeled ID. IDs are not inserted into narrative or requested from the model. Every queue item and every progress metric stays on its own Markdown bullet line. A queue count is the number of open entries, whereas recorded positions may have gaps. The primary report sections are separated by blank Markdown lines. Reject diagnostic dumps in BOTH model prose and fallback. Use product outcomes, not literal translations of evidence. In the fallback, prefer a deliberately plain sentence in an existing checkpoint display field before any ` | evidence: ` suffix, or explicit verified version, task names, statuses and uncertainty. Do not expose raw proof if a summary cannot be grounded. Current progress means verified scope, not estimate of hours remaining.

Prepared text, translations and publication receipts are process-local, not a second ledger. A natural root model context or child state change prewarms one tool-free native generation at a time. A report tool call reads the current canonical facts and uses only matching per-section translations if ready, otherwise current facts and cached names; it never waits for provider inference. Changed task names are keyed by source title/summary, not ID alone. Each section is cached against its own factual inputs; an active-lane change does not invalidate unchanged production evidence. Only changed sections/names are translated. Accept each readable model field independently. A missing or invalid field must not discard useful translations of other fields. Source titles already readable in Russian require no model call. A failed exact section/title input may be retried once at a different real boundary; repeated failures on unchanged input are suppressed until the relevant facts change or the reporting process resets. This applies only to optional reporting prose, never engineering. Logs distinguish model/API failure, invalid JSON, partial output and no readable fields; no raw response or secret is logged. Degraded reports use structured facts, concise Russian descriptions and explicit unknowns, never raw checkpoint/log prose. Blank lines separate sections; queue positions are stable recorded positions, not a contiguous count. A new boundary issues a fresh receipt/time; repeated calls within that boundary can reuse an unpublished identical result. A revision includes observed child identities/states as well as canonical files. When facts change during progress computation, retry local computation once, then mark unknown rather than certify a moving snapshot. Pending owner inputs are listed separately; validated registered-scope counters are explicitly partial, never a globally certified percentage or authorization. Invalid/stale source evidence still means unknown. A reset aborts auxiliary generation and discards old-session results. No prompt or source text is logged; model invocation start/result and timings are logged.

## Native contract enforcement and degraded mode

The existing Continuation Guard uses a primary `session.hook('context')` instruction to restore the report rule before actual Orchestrator calls, including after compaction. At `experimental.idle` it checks final `session.text.ended` parts for the current execution/receipt, with `session.context` as a read-only fallback. Full textual content AND Markdown line structure are required (only CRLF, trailing whitespace and surplus blank lines are normalized; receipt alone, flattened queue, missing section or extra status commentary do not count). This confirms structural textual delivery, not the actual Desktop rendering; tool, reasoning and synthetic messages are not publication. Success is logged only after this observation. If an active armed root with a genuine awaiting-children checkpoint missed the report, no owner admission/interrupt/permission barrier exists, and no ready independent work takes precedence, the hook may admit a single report-only native synthetic message for that state revision. This uses the existing storage state for deduplication. A genuine child completion or new owner input resets the correction opportunity; an unchanged missing report is not a loop. No report-triggered work assignment, interruption, permission or Human Gate bypass. Do not treat the synthetic text as owner input. Native events/permissions/ordinary engineering decisions retain priority. If the hook is unavailable or reports cannot be verified, log the degradation and let the ordinary workflow continue. The root completion event is a read-only verification fallback, not another wake-up mechanism. Experimental SDK contracts must be tested in the installed desktop; mocked tests do not establish live behavior.

The native tool uses `OPENCODE_PYTHON` if set, otherwise available standard Python 3 entrypoints, with a fixed argument vector to the existing installed progress tool, no shell or user-supplied command. It does not execute project code or change project files. Only a verified active primary root may invoke it; the model role itself has no tools. Preserve local config, provider settings and permissions. No global reasoning routing.

## Telemetry and speed

The existing `continuation-guard/events.log` records aggregate observed root/known-child execution duration, steps, first-token observations, tool calls, retries, compactions and job-update counts when matching native events are available, plus report generation time and publication/repair events. Log identifiers/timings only, no prompt or output bodies. Native V2 steps are correlated by assistantMessageID, tool calls by message and tool ID, and provider stream timing by session.step.streamed when available. Durations are observed event receipt intervals, not exact provider compute time. Missing start/finish/IDs and stream gaps mean partial measurements; overlapping model/tool/agent durations are not additive wall time. No timers or new data store for telemetry; existing log rotation remains. For comparison, use comparable tasks from intake to verified delivery and correlate task/Assignment/release evidence; do not equate a root turn's elapsed time with entire feature lead time. Inspect ready-to-dispatch delays, inter-role waits, corrective rounds and tool/model time before changing workflow. No claims of actual speedup before live evidence.

# Global OpenCode workflow policy

## Visible language contract — applies to every role and every turn

**All user-visible natural-language text MUST be in Russian by default, unless the current user or project explicitly requests another language.** This includes the first sentence of a new session, commentary before/after tool calls, brief handoff notices, progress updates, questions, explanations of errors, interim reports, final replies, and subagent text shown to the owner. A pre-tool remark like "I'll start by auditing..." is a language violation; say it in Russian. Do not change this requirement merely because an internal tool call or original prompt is in English.

**The agent instruction files and prompts themselves MUST remain written in English.** Internal tool arguments, code, commands, paths, API/schema identifiers, exact log lines and machine status values may retain their required original language. Do not force hidden reasoning into Russian; this policy governs visible prose. Translate/explain technical outcomes in Russian without altering literal commands, error messages, filenames or code identifiers.

This language contract is independent of reporting frequency/format and never triggers an extra agent call, tool invocation, pause or completion gate.

Applies across repositories; project-specific `AGENTS.md` and explicit user decisions can add constraints, not silently erase safety/acceptance requirements. This file defines cross-role invariants; each agent owns its specialist procedure. No role or document exists merely to satisfy a ceremony.

## Authority, sources, and durable state

### Unified owner-intent intake (chat AND user-owned files)

Before planning/delegating a **new task-affecting root-user instruction**, persist its provenance and reconcile its effect. Do not treat the input channel or message length as task priority: a sentence, screenshot correction, broad epic, cancellation, release instruction and follow-up can all change active scope. Ordinary greetings/status questions with no change to obligations need no record. Categorize semantically from the message **in conversation context**, not from trigger words/regex. A new message does not automatically create a new epic.

1. Preserve each material root input exactly once as an **immutable, safely redacted if secret-bearing** source file under `plans/owner_inputs/<unique-id>.md`; record origin/session/message reference, received time, referenced screenshots/assets and what could not be locally preserved. Never modify user-owned `current_task.md`; for changes made there, use an immutable relevant excerpt/snapshot with line/source anchors. Reuse a captured source on recovery; do not create a new entry merely because a session restarted. `runtime_task.md` is a pointer/summary, not a competing source of truth or a transcript.
2. Register the captured instruction in the existing `plans/progress_scope.json` **`owner_inputs` array** (optional for legacy scopes), with `id`, `source_path`, `source_sha256`, `kind` (`new_task|amendment|correction|cancellation|decision`), `target_task_ids`, `reconciled` (initially false) and a short `note`. This is an input index, **not an additional task list**. Link one input to multiple tasks if it affects them. A decision with no task target must specify an existing `recorded_in` artifact. For newly independent deliverables create one stable `tasks[]` row; for corrections/amendments update existing tasks/maps without adding fake epics, double-counting source clauses or discarding verified evidence. Keep historical IDs stable; never reuse a finished ID for unrelated work.
3. PM reconciles only the delta against maps, dependency order and already accepted decisions; mark `reconciled: true` ONLY after all affected obligations and exclusions are linked to task/map/decision evidence. Keep the input registered as pending while reconciliation runs: it must not disappear when Builder starts. On conflict, preserve both originals and apply the latest applicable explicit owner decision, with a trace, not silent overwriting. Already VERIFIED work remains proven unless the new requirement actually invalidates its acceptance.
4. Before published project-wide progress, handoff to a new session, final `DONE` or worktree integration, check for **unreconciled `owner_inputs`, unmatched prompt amendments, duplicate IDs, missing immutable sources and conflicting map ownership**. An incomplete intake makes the global scope/progress provisional, not permission to drop the new request. Do one bounded reconciliation at normal checkpoints; do not suspend unrelated active Builder/Reviewer lanes or trigger a recurring full-plan reindex.

`workflow_state.md` tracks only the current execution checkpoint and pointers; `backlog.md` contains deduplicated actionable items, not a second inbox. Feature maps/evidence remain the authority for verified acceptance. Old projects without `owner_inputs` remain compatible; backfill only concrete missing sources found during a bounded source-versus-scope audit, never invent historical messages or wholesale rewrite existing maps.

1. Latest explicit user instruction/correction is authoritative, followed by applicable user-authored `plans/current_task.md`, actual repository/runtime/evidence, agent-owned `plans/runtime_task.md` for active prompt-originated work, `plans/workflow_state.md` for recovery, then historical memory. Reconcile conflicts; never infer completion from an old status header.
2. `plans/current_task.md` belongs to the user: all agents may read/search it but MUST NOT create, edit, compact, clear, annotate, rename, delete, archive, or reset it. Old content can intentionally remain. Its mere existence never activates or completes work.
3. For non-trivial multi-turn prompt-originated tasks, keep a lossless recovery snapshot in an agent-owned task/source file; update the active snapshot when scope changes, do not append a transcript or overwrite other still-active source material. User corrections must be captured in the current coverage map without discarding already verified evidence.
4. `plans/workflow_state.md` is a compact CURRENT snapshot, not an append-only diary or a source of truth for completed reviews/deploys. Update in place after material transitions. Only genuinely running lanes belong under active work. Never erase proof from feature artifacts when removing stale active entries.
5. `plans/progress_scope.json` represents the distinct active owner-requested deliverables (including chat-originated amendments). Update scope before claiming a new overall percentage. Do not count archived/unrelated tasks, drop in-scope completed tasks, or reuse a stale denominator. Missing/mismatched coverage => explicitly uncertain count, not guessed progress.

## Requirement integrity and strict acceptance

For non-trivial work, PM creates/reconciles a source-to-requirements map and checks both directions, including prose, tables and screenshots. Run the existing `<OPENCODE_CONFIG>/tools/requirements_gate.py` with `--stage plan` before Builder, `--stage review --slice ... --candidate ...` before approval, and `--stage release --candidate ...` for completion with the actual Git repository/candidate. Respect old map compatibility; opt in to `strict_evidence`/slice graph only with a real evidence convention. On strict maps verify that the candidate commit exists in the actual Git repository, candidate-bound evidence references an existing repo-relative artifact (with content digest when specified), graph dependencies are acyclic, and writer scopes do not have unaccounted overlaps. A failed strict check is not a reason to disable strictness. Missing mapping, drift or failed gate routes to repair, not `DONE`.

A task is `DONE` only when **all mandatory engineering acceptance** is verified against the implemented, reviewed and (where required) deployed candidate. Tests, a PASS claim, a generated map, a fallback/degraded mode or a completed subagent do not alone prove acceptance. Preserve `FAILED`/`PENDING` until supporting evidence exists. A slice's approval never implies the parent is complete. Reviewer is independent and retains veto on mandatory defects.

`owner_optional` is only for genuinely voluntary owner observations grounded in an explicit applicable user decision AND linked to retained mandatory engineering checks. Such observations do not block engineering `DONE`, release or the progress denominator; never relabel a real mandatory live test or technical defect to optional. Only explicit, applicable project-specific owner decisions can make owner observations optional; all agent-executable engineering checks remain mandatory. Respect project rules prohibiting live messages or production side effects.

A correction/review rejection or failed production check must keep exact findings and route to the responsible executor: application/behavior/data -> Builder; packaging/infrastructure/deployed-source/harness -> DevOps; proven clerical mapping/evidence binding only -> PM; Architect for actual contract decisions or repeated non-progressing repairs. Fix -> focused re-verification -> independent Reviewer -> safe release as appropriate. Do not lower tests/acceptance to get a green result. Keep the last verified release while unapproved changes are fixed. A failed audit/report does NOT terminate available repair work. Limit repeated attempts and diagnose root cause instead of looping.


## Closure-first delivery and proportional review — no paperwork treadmill

Accepted implementation and VERIFIED evidence must be reflected in the owning requirement map and central progress index at the **same normal handoff**, not deferred into an open-ended second acceptance project. Reviewer owns the behavioral verdict; PM/Orchestrator own accurate status/evidence binding. Where Reviewer has already approved the exact relevant candidate and auditable evidence exists, reconcile the *affected rows only*, without repeating the build, whole-epic review or regenerating plans. A row with no actual proof remains PENDING/FAILED; never fabricate VERIFIED, silently shrink owner acceptance or count voluntary owner observations as mandatory.

Separate **feature/slice release** from **epic/parent DONE**. A complete, independently reviewed slice may ship with its mandatory dependencies and production checks even while unrelated slices or later owner instructions remain open; explicitly report the rest as open. Use scoped release checking only where a real dependency graph and exact candidate/proof make it safe. Full parent completion still requires every required item verified. Do not gate a finished slice on unrelated pending backlog or preliminary design for the next wave.

Reviewer must distinguish reproducible contract/regression/security defects from subjective prose/style preferences, advisory refactors, pre-existing unrelated minor defects and evidence bookkeeping. Only material in-scope failures block that candidate; nonblocking observations go once to the deduplicated backlog. No arbitrary exemption for actual failed behavior (e.g. FREQUENT failures), no endless full regression suite or re-review of unchanged mechanisms. Repeat focused tests on changed behavior and impacted integration paths; enlarge scope only on specific evidence of blast radius.

Do not create one new epic/approval/requirements sweep for each review nit or user correction. Keep scope stable within a candidate; new explicit owner requirements are registered and placed in the right feature/dependency wave, not silently discarded and not automatically inserted into an unrelated release gate. When a blocker repeats despite fixes, use evidence-led root-cause diagnosis and a different concrete remediation, not another identical review loop. Every report is a view of execution, never the execution's stop signal.

## Distinguish completion, open inventory, and executable work

A 90% requirement count and an empty *runnable* queue can both be accurate. Never make the count 100% by bulk-relabelling `PENDING`, `FAILED`, timed production checks or unproven owner requests. At a normal close-out checkpoint classify each outstanding group from existing maps/evidence into: (1) real immediately executable repair/acceptance, (2) active child work awaiting a real join, (3) a documented future external/owner dependency, or (4) a strictly optional owner observation already excluded from mandatory engineering totals. If there is unexplained residual mandatory scope, assign **one bounded** PM/Reviewer reconciliation task, not recurrent final reports. Reconcile already-approved candidate evidence once, not through a duplicate release or full re-review. Preserve original source IDs and actual failures.

Continuation Guard must rely on the explicit machine-readable `Next execution: runnable|awaiting_children|none` state in `plans/workflow_state.md`, not just the existence of `PENDING` rows. A pending task is an inventory fact, NOT a wake-up signal. `none` suppresses autonomous prompt injection; `awaiting_children` requires a real completed-child barrier; `runnable` requires a grounded next action. The coordinator updates this field at ordinary checkpoints, never to force an idle loop. This rule adds no model agent, approval stage or new project file.

## One portable workflow-owned storage root and epic-close housekeeping

**Scope:** all agents, all stacks/projects, local development only. Resolve `<GLOBAL_CONFIG>` from the actual installed global OpenCode configuration containing this AGENTS.md; never hardcode a user, drive, project name, a project-parent path or an OS-specific cache path. All **workflow-created** throwaway data belongs under `<GLOBAL_CONFIG>/WorkspaceData/` (the single owned storage root). New worktree checkouts, disposable Git clones, local backup snapshots, cache/index data, generated probe results, temporary reports, exports, debug logs, screenshots and intermediate files must be created there, or in the current canonical project root **only when they are intentionally durable project source/tests/config/review evidence**. Never create temporary siblings beside the project or under arbitrary home/OS temp paths. A project may be Python, Go, a Minecraft mod, or any other stack.

Use `<GLOBAL_CONFIG>/tools/workflow_housekeeping.py init` once as needed, `allocate --repo <canonical-project> --epic <stable-epic-id> --kind temp` for throwaway runs, `worktree-path --repo <canonical-project> --epic <stable-epic-id>` followed by `git worktree add`, then `register-worktree --repo ... --epic ... --path ...` to bind ownership. The bundled global `workflow.intelligence` plugin routes its own index, shell temporary directories and controllable language package caches to WorkspaceData. Where the platform or an external tool unavoidably writes unmanaged system data, disclose the limitation; **do not claim instructions can override every program's native cache or operating-system storage**. Do not rewrite a user's environment globally to enforce this.

**Epic completion is the cleanup trigger, not a TTL, hourly schedule, or every tiny task.** After all epic children are joined, required evidence is promoted, review/release state is reconciled, and no agents still use that epic's temporary areas (for shared-cache deletion, no agent may be using that project's cache at all), the responsible Builder/DevOps runs `epic-close --repo ... --epic ... --purge-disposable-cache` in dry-run, then `epic-close ... --purge-disposable-cache --confirmed-complete --confirmed-idle --apply`. The script deletes only tool-marked owned disposable runs and Git-registered, clean, provably integrated, inactive worktrees. Keep anything dirty, unmerged, unique, active, unknown, symlinked, or containing databases/credentials/backups. Never use `git reset --hard`, `git worktree remove --force`, recursive deletion of unknown directories, or wipe `plans/`/source/review evidence. An unsafe or locked item is retained and reported without blocking otherwise-valid work or spawning a new human gate.

**One-time legacy cleanup:** user-visible inventory of old sibling folders and historical `OpenCodeCache`/`OpenCodeScratch` first; verify every candidate's provenance, Git registration and branch/commit integration, working-tree dirtiness, ownership and backup uniqueness. Retire safe legacy worktrees with Git, not filesystem deletion. Delete isolated proven-disposable cache and scratch only after confirming no consumer and no unique source/data; preserve uncertain items for review. Never infer deletability from name, age or size. Never access, clean or modify the production server for a local workspace hygiene task. Use the current project root and actual global config, not example absolute paths.

## Orchestration versus session turns — no contradictory commands

**Task status and model-session turn status are different things.** `in_progress` can remain true while the root turn yields to a live subagent, user/platform event, or temporary model/provider interruption. Yielding a turn does NOT mark `DONE`, abandon work, or prove a blocker.

- **Runnable work exists**: dispatch the real next permitted specialist/tool action; a progress report or state update is not a dispatch.
- **Work only in active child sessions**: preserve the join/session IDs and **yield without busy-waiting, repeatedly polling or manufacturing keep-alive calls**. Resume on a genuine completion/re-entry event and reconcile results exactly once. Never assert that OpenCode is guaranteed to wake the root session; an installed Continuation Guard is only an auxiliary recovery mechanism.
- **Nothing runnable**: record the true verified state (`WAITING_EXTERNAL`, unresolved real Human Gate, provider/platform interruption, or fully `DONE`), exact re-entry condition/owner and any independent work still possible. An idle dependency is not permission to invent success.
- Large session/token counters, completed reports, and finished deployments are never themselves evidence that the task is `DONE`; reduce context using compact checkpoints/native compaction where available. Do not force the model to choose between an impossible endless active turn and a false final completion.

Prefer a foreground/joined call for the single critical result when the OpenCode runtime supports it; independent preparation can run in the background. If a native join/wake is unavailable, record durable state and use supported completion/recovery events. Never busy-loop, repeatedly call models to "keep alive", or duplicate an in-flight lane.

## Real Human Gates and standing decisions

Ask the owner only when the source and latest decisions do not already answer a material owner-only choice/action (cost, data/privacy, irreversible/destructive permission, missing authorization or genuinely required manual device acceptance). Technical ambiguity, review failure, old `BLOCKED_REAL_HUMAN_GATE` labels, voluntary observations, ordinary deployment and external waits are not reasons to request permission. PM/Architect/Orchestrator must compare prior equivalent decisions and reconcile duplicate questions. Only genuinely unresolved questions belong in `plans/owner_questions.md`; state the exact choice/action and dependent work. Use primary-session native `question` when actually available, otherwise ask plainly in chat; proceed with unrelated safe work.

**Project-specific release authorization is never a global default:** use explicit current-project permissions; absent such authorization, follow the project's normal approval/release policy.

## Parallel code safety

Parallelize genuinely independent work: default up to 3 writers with disjoint write scopes, 3 read-only preparation lanes, 6 total only if useful. Keep the active implementation/review/deployment on one exact candidate. Serialize shared DB migrations/schema, lockfiles, routers, release metadata and overlapping files. Background preparations may read the same sources; they must not mutate the candidate being reviewed. Do not start agents just to fill the concurrency budget.

## Quality, skills, repository intelligence and research

- **Known documents first:** for `plans/current_task.md`, `plans/workflow_state.md`, `plans/progress_scope.json`, feature maps, reviews, and `git status/log`, use direct file-system/Git reads. `workflow_intel` is a *nonessential symbol/impact navigation cache*, not a workflow-status reader or mandatory startup prerequisite. Its `locate` action searches **code symbols**, not filenames. Do not call it for a known `plans/` path; do not make a paired `stats` + `locate` call to establish the workflow state.
- For code navigation use current Git/code/runtime, native LSP if available, optional `workflow_intel` for genuine symbol/reference/impact lookup, then targeted grep/read, broad scan only if necessary. On cache-tool unavailable/error/timeout, record the failed optional lookup at most once and **immediately continue with direct file reads / Git / targeted search**. A cache failure is not a blocker, not a Human Gate, and not permission to end the active task. Cached locations are hints, not evidence. configured memory answer durable past decisions, not current symbol lookup; retrieve few source-backed items and verify them.
- Global `architecture-design` and `code-quality` skills are optional, language-neutral, loaded with OpenCode's native `skill` tool only when they help a substantive decision or non-trivial code-quality risk. No extra phase, ritual ADR, unsupported fashionable patterns, forced dependency or refactoring for style alone. Build to the detected host/language conventions.
- For changing external API, provider, SDK or platform semantics, verify the precise claim with accessible current authoritative documentation (Context7, Exa, DuckDuckGo, native web tools as available). No fabricated tool availability or claimed verification. Do not search the web for facts proven by repository code.
- New permanent tests protect actual contracts/regressions/integration seams; provisional test artifacts must be resolved before approval. Do bounded test-portfolio audits only when growth/flakiness/obsolete patterns justify one; green tests do not supersede owner requirements. Fix the smallest mechanism that satisfies the contract; independent Reviewer confirms.
- Transient probes/screenshots/logs go into managed `OPENCODE_WORKFLOW_SCRATCH` when possible. Promote only durable evidence. Never clear unowned filesystem paths or reset other agents' work. Credentials are not copied into reports, files or logs.

## Owner reporting — presentation only

All owner-facing prose (including short substantive updates) must be **plain, accurate Russian**, intelligible without reading internal ticket codes. Explain what changed in the product, why it matters, what was actually verified, who is working now, what follows and whether owner action is required. Avoid opaque `lane/gate/ledger/SHA/EXIT 0` as the main story. Uncertainty, failures and incomplete checks must remain visible; do not invent confirmations.

For **every substantive owner-facing status message** (including a short update while Builder/Reviewer is running, resumed session and handoff), show system-local time with UTC offset, task and requirement progress when verified, and a **20-cell ASCII progress bar on its own line**. Do not classify a short status as exempt. If numeric data are missing or stale, display `[????????????????????]` with an explicit `progress unavailable/stale` label instead of inventing percentages. Very short pre-tool narration is optional; if a status message is sent, apply the full lightweight format. Use `<OPENCODE_CONFIG>/tools/workflow_progress.py --scope-file plans/progress_scope.json` or an equivalent still-fresh result; reuse a still-current read-only snapshot when possible; obtain one at the next normal checkpoint if stale. Never block a ready agent call or launch another agent just to format a report. If counts are unavailable, say so rather than reuse stale totals. Optional owner observations are a separate count. Technical evidence stays in feature artifacts.

Reports are a read-only view, **never a phase, join barrier, Human Gate, timer, reason to stop, or trigger to start a separate agent**. First dispatch any runnable next action, then present a concise truthful snapshot if an update is materially useful. A root turn may legitimately yield to running workers; this is not a completed task. Reporter is not required by this policy and must not be invented merely to format text.

## Tool paths and document economy

`<OPENCODE_CONFIG>` means the actual global OpenCode configuration directory, NOT the application repo and NOT a literal shell variable. Resolve its location once. For bounded project state, update existing sections/snapshots in place rather than adding endless `NOTE` blocks, duplicating evidence or clearing user-owned files. Keep the backlog to unresolved issues and preserve referenced evidence/history.

## Public installation and permissions boundary

This public template is language- and project-agnostic in its engineering workflow. Its visible reply language is Russian by default, but an explicit project/user choice may set another language. No production URL, host, account, release bypass, private plugin or stored credential is assumed. Only configure optional integrations (MCP, repository-index plugin, Continuation Guard) when available in the user's installation. A local housekeeping tool must not touch production, the primary project root, unknown folders or unregistered worktrees.

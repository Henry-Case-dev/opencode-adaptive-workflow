# Reporter and native Report Contract — Lean v3.5

## Public configuration

The public template keeps automatic continuation disabled by default. To activate native Reporter, telemetry and continuation, explicitly set `enabled: true` in the existing `plugins/continuation-guard/config.json` and restart OpenCode safely. `reportEnabled` defaults to true when the guard is enabled; set it to false to opt out of native reporting. Do not replace personal provider/model/MCP configuration. External MCP Events is unrelated and remains opt-in. The runtime requires the supported OpenCode V2 plugin APIs; if unavailable use the degraded reporting path.

## Ownership and boundary

Reporter is a separate communication role with its own `agents/Reporter.md`. The normal transport is the existing Continuation Guard's `workflow_report` native tool, using OpenCode's `ctx.experimental.generate.text` with the actual root model and a compact data-only prompt. It does not create a session, use tools, keep a transcript, switch models or change reasoning. The role file also supports explicit one-shot native subagent delegation with supplied facts only; do not use both for one report. No new tabs, long-lived reporter branch, installation script, new MCP server, queue, watcher, or project report database.

At each substantive primary status/release and each wait boundary, Orchestrator first processes real events, dispatches ready safe engineering and checkpoints the canonical state. It then invokes `workflow_report` once through the native tool or actual Code Mode with `canonical_root` equal to the verified planning checkout. Publish the returned text verbatim in the main assistant message. Do not rewrite, abbreviate, omit the full queue, calculate percentages or obtain a shell clock. If unavailable, publish a degraded human-readable report from verified data, clearly marking unknown values. Reports never confer authority or block Builder/Reviewer/DevOps; no reporting-specific commits, approvals, task rows, cleanup worktrees or progress resets.

The current implementation accepts the root session's actual location only, and refuses a different supplied planning root instead of silently reading a worker/release snapshot. If the canonical planning checkout differs, use a manually verified degraded report from that checkout and continue normal engineering. Record the canonical root on recovery as before. Do not change planning ownership to make a report work.

## Facts and presentation

- `progress_scope.json`: all open tasks in recorded queue order, including blocked, parked and unregistered-position rows. Missing names/positions/dependencies are not invented. `VERIFIED` and `CANCELLED` are not open rows.
- `workflow_state.md`: current compact header and actual lane/next/last verified/production evidence references. It is a checkpoint claim, not remote runtime proof. At real release record version/SHA/evidence in `Production:`; optional `Last completed:` names the actual result. Existing files/maps remain authoritative.
- Existing `workflow_progress.py --scope-file ... --require-queue --json`: global task/slice/requirement counts and certification. Unmeasurable or invalid ratios get `[????????????????????]`; never compute percentages from `BUILDING` or omitted rows. Source/map parsing and hash reuse is strictly within a single invocation; concurrent changes invalidate it.
- One report includes local system time + UTC offset, exact counts/20-cell bar, production, completed work, current feature/role/work, next action, blockers, owner action and complete open queue. The renderer owns time, arithmetic, queue order and exact ID coverage. Reporter translates task IDs into plain Russian, not inventing facts. Technical IDs stay in parentheses for traceability. Current progress means verified scope, not estimate of hours remaining.

Prepared text is held only in process memory, associated with root and state revision. An unchanged unpublished snapshot reuses its prepared report; once published, the next real boundary can generate a fresh time/report. When files change during generation, recompute deterministic facts once, use a degraded narrative, and refresh at the next real boundary; do not loop. Provider/API/model failure produces deterministic data-only fallback. Reporter receives no tools, raw chat history, env, credentials or arbitrary source files. Existing task title/summary and checkpoint metadata are sufficient inputs; when missing, explain uncertainty. Use the normal plan/source process to improve metadata during real work, not a new mapping project.

## Native contract enforcement and degraded mode

The existing Continuation Guard uses a primary `session.hook('context')` instruction to restore the report rule before actual Orchestrator calls, including after compaction. At `experimental.idle` it checks whether the exact prepared report appears in the parent assistant text (`session.context`); tool, reasoning and synthetic messages are not publication. Success is logged only after this observation. If an active armed root with a genuine awaiting-children checkpoint missed the report, no owner admission/interrupt/permission barrier exists, and no ready independent work takes precedence, the hook may admit a single report-only native synthetic message for that state revision. This uses the existing storage state for deduplication. A genuine child completion or new owner input resets the correction opportunity; an unchanged missing report is not a loop. No report-triggered work assignment, interruption, permission or Human Gate bypass. Do not treat the synthetic text as owner input. Native events/permissions/ordinary engineering decisions retain priority. If the hook is unavailable or reports cannot be verified, log the degradation and let the ordinary workflow continue. The root completion event is a read-only verification fallback, not another wake-up mechanism. Experimental SDK contracts must be tested in the installed desktop; mocked tests do not establish live behavior.

The native tool uses `OPENCODE_PYTHON` if set, otherwise available standard Python 3 entrypoints, with a fixed argument vector to the existing installed progress tool, no shell or user-supplied command. It does not execute project code or change project files. Only a verified active primary root may invoke it; the model role itself has no tools. Preserve local config, provider settings and permissions. No global reasoning routing.

## Telemetry and speed

The existing `continuation-guard/events.log` records aggregate observed root/known-child execution duration, steps, first-token observations, tool calls, retries, compactions and job-update counts when matching native events are available, plus report generation time and publication/repair events. Log identifiers/timings only, no prompt or output bodies. Missing start/finish/IDs and stream gaps mean partial measurements; overlapping model/tool/agent durations are not additive wall time. No timers or new data store for telemetry; existing log rotation remains. For comparison, use comparable tasks from intake to verified delivery and correlate task/Assignment/release evidence; do not equate a root turn's elapsed time with entire feature lead time. Inspect ready-to-dispatch delays, inter-role waits, corrective rounds and tool/model time before changing workflow. No claims of actual speedup before live evidence.
